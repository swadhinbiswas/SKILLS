# Migration tool workflows

Exact commands and the configuration each tool needs for online DDL. Verify
subcommands and flag names with `<tool> --help`; they drift between major
versions.

## Alembic (Python, SQLAlchemy)

Autogenerate diffs the metadata against the database, so it misses anything
the ORM cannot express and can propose destructive changes.

```sh
alembic revision --autogenerate -m "add risk_score to orders"
alembic upgrade head            # apply
alembic downgrade -1            # roll back one
alembic downgrade base          # roll back everything
alembic current                 # what is applied, per database
alembic history --verbose
alembic upgrade head:5f3a2b    # upgrade to a specific revision
```

`op.create_index(..., postgresql_concurrently=True)` needs
`op.execute("COMMIT")` around it and a migration that does not run inside a
transaction block. Configure that in `env.py` with
`context.configure(transaction_per_migration=False, ...)` plus
`connection.autocommit_block()`, and set `transactional_ddl = False` on the
engine. Without this, `CREATE INDEX CONCURRENTLY` fails with
`cannot run inside a transaction block`.

Autogenerate traps:

- Server defaults added in the DB by hand appear as a `remove_column` or
  `alter_column` diff. Always read the generated file before committing.
- Renaming a column is autogenerated as drop + add. Turn it into
  `op.alter_column(..., new_column_name=...)` by hand.
- `op.bulk_insert` for reference data, never a per-row `op.execute`.
- Data backfills belong in the migration only if they are small; otherwise a
  separate resumable job, and the migration only guards the invariant.

## Flyway (Java, any engine)

```sh
flyway -url=jdbc:postgresql://db:5432/app -locations=filesystem:./sql \
       -baselineOnMigrate=true info
flyway -url=... migrate
flyway -url=... validate      # checksum + ordering check
flyway -url=... repair        # updates checksums; use only after a real audit
flyway -url=... undo -target=V3   # Flyway Teams/Enterprise only
flyway -url=... redo           # Teams/Enterprise only
flyway -url=... outoforder=false
```

Naming: `V1__create_orders.sql`, `R__seed_dim_currency.sql` (repeatable),
`U1__drop_legacy.sql` (undo, Teams/Enterprise). Placeholders:
`${flyway:defaultSchema}`, `${table}`.

- SQL migrations run in a transaction by default on engines that support DDL
  in transactions. A PostgreSQL migration containing `CREATE INDEX
  CONCURRENTLY` fails with `cannot run inside a transaction block`; the fix is
  a script-level `\!` or a per-migration opt-out configured with
  `flyway.executeInTransaction=false` (a script config file next to the SQL).
- `validate` in CI is cheap insurance: it fails the build on checksum drift and
  out-of-order versions before a deploy can.

## Prisma (TypeScript)

Prisma generates SQL from its own migration history, so hand-written DDL is
normally a mistake — but `prisma migrate diff` exists for exactly that.

```sh
npx prisma migrate dev --name add_risk_score    # local only; may reset data
npx prisma migrate deploy                        # production / CI; no prompt
npx prisma migrate status
npx prisma migrate resolve --applied <name>      # mark a hand-run migration done
npx prisma migrate resolve --rolled-back <name>
npx prisma migrate diff \
  --from-schema-datasource prisma/schema.prisma \
  --to-schema-datamodel <datamodel> --script
```

- `migrate dev` is interactive and **will reset the database** if it detects
  drift. It must never be pointed at production.
- `migrate deploy` applies pending migrations and fails if the database is
  behind in a way that requires baselining.
- Prisma has no `NOT VALID`. For large Postgres tables, drop the
  `@default`/required marker out of the migration SQL and add the constraint
  with a follow-up hand-written migration.
- Shadow database: `migrate dev` creates one to detect drift; on Postgres it
  needs `shadowDatabaseUrl`.

## golang-migrate

```sh
migrate -path migrations -database "$DATABASE_URL" up
migrate -path migrations -database "$DATABASE_URL" down 1
migrate -path migrations -database "$DATABASE_URL" version
migrate -path migrations -database "$DATABASE_URL" force 7
migrate -path migrations -database "$DATABASE_URL" -verbose up
```

Files: `000004_add_risk_score.up.sql` / `.down.sql`. `force` marks a version
applied or rolled back without running it — the correct tool after a failed
production migration, and the wrong tool as a shortcut for a skipped one.

- No checksum validation. That makes renumbering and squashing harmless for
  golang-migrate specifically, but it also means drift is invisible: run
  `version` in CI and compare against a checked-in expectation.
- Each migration runs in its own transaction (driver permitting). A file that
  needs `CONCURRENTLY` must disable it explicitly.

## Django

```sh
python manage.py makemigrations <app>
python manage.py sqlmigrate <app> 0007   # print the SQL, read it
python manage.py migrate <app> 0006
python manage.py showmigrations
python manage.py migrate <app> 0005 --plan   # what would run
```

- `makemigrations` autodetects; always `sqlmigrate` and read the SQL. It
  silently produces `DROP`/`RENAME` for column renames and does not know
  about `NOT VALID`, `CONCURRENTLY`, or functional indexes.
- Add `db_index`+`condition` for partial indexes, or use `SeparateDatabaseAndState`
  for anything Django's schema editor cannot express.
- `migrate app 0006` targets a specific app; forgetting the target applies
  everything. Use `--plan` first.
- `--fake` / `migrate app zero --fake` only when the change was applied
  out-of-band on purpose.

## Rails

```sh
bin/rails generate migration AddRiskScoreToOrders risk_score:integer
bin/rails db:migrate
bin/rails db:rollback STEP=1
bin/rails db:migrate:status
bin/rails runner 'puts ActiveRecord::Base.connection.migration_context.current_version'
```

- Rails wraps each migration in a transaction; `disable_ddl_transaction!` at
  the top of the class is required for `add_index ..., algorithm: :concurrently`
  and for `algorithm: :immediately`.
- `add_reference ..., foreign_key: true` validates immediately in older
  versions; use `validate: false` (newer Rails) plus a later
  `validate_foreign_key` to get the `NOT VALID` behaviour.
- Migrations are permanent classes: edit only unreleased ones. Every generated
  migration has an auto-`down`, which is only trustworthy if the change is
  actually reversible.
- `ActiveRecord::Migration[7.1]` etc. in the class header pins behaviour; bump
  it deliberately, not with a blanket search-and-replace.

## Knex (Node)

```js
exports.up = async (knex) => {
  await knex.schema.alterTable('orders', (t) => {
    t.integer('risk_score').nullable();
  });
};
exports.down = async (knex) => {
  await knex.schema.alterTable('orders', (t) => {
    t.dropColumn('risk_score');
  });
};
```

```sh
knex migrate:latest
knex migrate:rollback --all
knex migrate:status
knex migrate:make add_risk_score
```

- Knex wraps a batch in a transaction and has a `disableTransactions` config
  option per environment — set it for migrations that need
  `CREATE INDEX CONCURRENTLY`.
- `knex migrate:up` on a partially applied batch rolls the whole batch back;
  the "down" must be truly reversible or you will be stuck.
- A unique index created in the same `alterTable` as a `unique` constraint can
  fail; add the index separately and name it.

## Liquibase (Java, changeSets)

```sh
liquibase --changelog-file=changelog.xml --url=jdbc:postgresql://db/app \
         status
liquibase update
liquibase rollback -count=1
liquibase tag v2.4
liquibase history
liquibase calculate-checksum
```

- `changeSet` needs an `id` and `author`; `runOrder` controls ordering when
  `logicalFilePath` is shared. Contexts (`context="prod"`) let one file carry
  environment-specific steps.
- `preConditions` with `onFail="MARK_RAN"` / `HALT` gives you "apply only if
  the DB is in the expected state" — the closest thing to a safety gate.
- `addForeignKeyConstraint` with `constraints` + `baseTableName` … for
  unvalidated FKs use `addNotNullConstraint` with `columnDataType` and run
  Liquibase with `runInTransaction=false`; verify the exact attributes for
  your Liquibase version before relying on it.
- A changeSet is executed once and recorded by identifier + checksum. Liquibase
  will skip a changeSet that was applied and then changed, and tell you to
  `clearCheckSums` — only after confirming the DB is genuinely correct.

## Generic rules across all of them

- Generate SQL and read it. Every one of these tools can produce a table
  rewrite from an innocent-looking line.
- Set a `lock_timeout`/`lock wait timeout` in the connection that runs DDL.
- One deploy = one additive change. Backfills run outside the migration, in
  batches, and are resumable.
- Keep the rollback in version control next to the migration, and mark
  irreversible ones explicitly in the migration comment.
- A migration that has been applied is history. Fix forward with a new file.
